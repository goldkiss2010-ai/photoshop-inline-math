# 検証と実機確認

## 自動試験

PythonとNode.jsを用意し、次を実行します。自動試験にPhotoshopとTeX本体は必要ありません。

```powershell
uv run --no-project --python 3.13.15 --with fonttools==4.67.0 python tools/run_partial_integration_tests.py
```

コード混在35例×LF/CRLF/CR、Python/JavaScriptの解析一致、部分成功、書式投影、復元、OTF/対応表、フォント出所、通知ZIP、保存先、CCX照合、配布ZIPを確認します。Windows専用テストはPowerShellの構文と、外部プロセスを模擬したインストール起動・分岐を確認します。Adobeへの実インストールは自動試験では行いません。

2026-10-15の分離版では、LinuxでPython 78件成功・Windows専用6件はスキップ、UXPのJavaScript 290件成功。実CCXのソース照合と配布ZIPの生成・全ファイルのハッシュも確認しました。Windows専用テストはこのローカル環境では実行していません。

配布ZIPを一時フォルダーへ展開し、外部の空データ保存先でLinuxの実TeX/SVG/OTFによる冷起動とAPI応答も確認しました。本体147ファイルは不変で、制作データは外部だけに生成されました。Windowsの初回導入を代替する試験ではありません。

CIはLinuxの統合試験とWindowsのランチャー試験を定義しています。CIでの実行結果とローカルの成功は別に記録します。初回の[Actions実行](https://github.com/goldkiss2010-ai/photoshop-inline-math/actions/runs/38692843246)は両ジョブともrunner名・実行stepが空のまま失敗し、テストは開始されていません。原因はこの記録だけでは確定できません。

### 公開後のWindows CI呼び出し（2026-10-16）

[公開直後のCI](https://github.com/goldkiss2010-ai/photoshop-inline-math/actions/runs/38826077183)では、Linuxの統合試験・CCX照合・配布ビルドが成功しました。Windows側は、`Get-FileHash` が見つからない失敗と、日本語出力をcp1252として読むデコードエラーで停止しました。

テストを起動するPowerShell 7の `PSModulePath` がPythonを介してWindows PowerShell 5.1へ渡り、互換性のないモジュールを優先してしまう条件を修正します。テスト子プロセスだけの環境からこの変数を外し、Windows PowerShellが既定の検索先を組み立てるようにします。対処の根拠は[Microsoftの説明](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_psmodulepath#starting-windows-powershell-from-powershell-7)です。

テスト用スクリプトはUTF-8 BOM付きで保存し、PowerShellの出力とPythonの読み取りもUTF-8へ揃えます。これらは `tests/windows_test_support.py` に共通化します。アプリのランチャー・CCX・確定した配布ZIP・公開タグは変更しません。このテストはExplorerから起動する際の既定モジュール環境を再現し、PowerShell 7からCMDを介して起動する経路の確認は含みません。

## OTFファイル名の改善（2026-10-16）

先行した日本語Family名の試験後、実機画像に「Photoshopが期待したPostScript名のフォントを返しません」と表示されました。停止はPostScript照合の段階で、画像だけで根本原因は確定していません。利用者が求めていたのはエクスプローラーのOTFファイル名だったため、新規作成のFamily/PostScript名は従来のASCII名へ戻しました。試験版schema 2の読込みは残し、既存試験データは変更しません。

現在はインストール用のローカルコピーとZIP内のOTFに、表示名＋8桁IDの日本語ファイル名を付けます。生成済みOTFの中身は変えません。コピー元とのバイト列一致、表示名変更後のコピー、古いコピーの置換、元のOTF・対応表・生成情報の不変、未生成・不一致時の停止、ZIP内のファイル名・ハッシュとHTTP起動先を試験しています。

ローカルLinuxの全体試験はPython 89件成功・Windows専用6件スキップ、UXP JavaScript 290件成功。Linuxの実TeX→SVG→OTFでも、ASCII内部名での日本語ラベルの新規作成、日本語ファイル名のコピーとZIP、元OTFとのバイト列一致を確認しました。

2026-10-16、日本語ファイル名への修正後、新規フォントを生成して更新先を開く確認手順に対し、利用者から「確認しました」と報告を受けました。エクスプローラーでのOTFファイル名の確認完了として記録します。この報告を、インストール・Photoshop適用・PSD再オープンの各項目を個別に確認した記録へは広げません。

パネルのソースは変更しておらず、既存0.8.2 CCXを継続使用できます。前回のschema 2試験フォントを使う場合、そのFamily名はそのままです。今回の実機確認には新しい管理フォントを作成します。

## リリース候補の実機スモークテスト

1. 配布ZIPを新しいフォルダーへすべて展開し、セットアップを完了する。
2. 通常のCCXインストールを試す。確認画面が開かない環境で代替ランチャーを試す。
3. UDTの開発版をUnloadし、UDTを閉じる。
4. Startから起動し、Photoshopの「プラグイン」メニューからパネルを開く。
5. 制作フォントを作成し、`本文 $x_i^2$ と $\frac{a+b}{c}$。` を変換する。案内に沿ってOTFを導入して適用する。
6. 同じレイヤーでLaTeXへ復元し、本文とコードを保持することを確認する。
7. [混在サンプル](../examples/math-input/README.md)で改行・ブロック混在・保留の理由を確認する。
8. 表示名変更と通知付きフォントZIP保存を行い、OTFと対応表が揃うことを確認する。
9. PSD保存・Photoshop再起動後にパネルを開き、PSDの表示と往復を確認する。
10. 別のWindows環境で同じ手順を行う。空白・日本語を含む展開先でも確認する。

失敗した場合は、入力・Photoshop/CCの版・点検出力・パネルの診断を組み合わせます。機能の失敗と、Adobe側のCCX導入失敗は分けて記録します。
